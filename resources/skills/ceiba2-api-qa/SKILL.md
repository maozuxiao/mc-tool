# Ceiba2 / WCMS5 API 报错排查

## 适用场景

客户或集成方反馈「调 Ceiba2（WCMS5）API 失败」：报错、拿不到数据、视频打不开、下载任务失败、证据查不到、鉴权失败等。
你的任务是**给出可执行的定位结论**（可能原因 + 依据 + 下一步），而不是回一句「请检查参数」。

## 铁律

1. **不许编造**：errorcode 含义只以本文件 / `error_codes.md` 为准。文档没有定义的返回（如 HTTP 401/404/500）要明确说是 **HTTP 层问题，不属于文档定义的 errorcode**，并给网络/服务侧排查。文档里没说过的行为，宁可写「文档未定义，需研发确认」。
2. **先定层级，再谈原因**：① 网络层（连不上/超时/404/5xx）② 鉴权层（key 缺失/无效/过期/无权限）③ 参数层（缺参/类型/格式）④ 业务层（无数据/无设备）⑤ 设备层（离线/服务忙/执行失败）。
3. **每条结论都要有依据**（错误码 / 文档章节号 / 字段名）+ **下一步动作**（客户补什么信息、改什么）。

## 参考文档怎么读（务必先看这条）

本技能的 4 份参考文档（`error_codes.md` / `cases.md` / `api_reference.md` / `api_full.md`）放在**技能目录的 `references/` 下**，它们的**绝对路径已由系统提示给出**（形如 `…\resources\skills\ceiba2-api-qa\references\error_codes.md`）。

- ✅ 用 `file_read` 读时**照抄那个绝对路径**（含盘符）。
- ❌ 不要写相对路径（`references/error_codes.md`）：文件工具的相对路径是按**当前工作区根**解析的，会解析成 `<工作区>/references/…` → 报 `路径不存在（PATH_NOT_FOUND）`。
- 若确实读不到（例如提示 `PATH_OUTSIDE_ROOT`），就**只用本文件**排查 —— 常见场景本文件已覆盖，不必反复重试读文件。

## 第一步：先收信息（缺哪项就直接问客户）

| # | 要客户提供 | 用途 |
|---|---|---|
| 1 | 完整请求 URL（含域名与端口）+ 方法（GET/POST） | 定位接口、核对路径拼写 |
| 2 | 完整请求参数（**含 key**：GET 的 query、POST 的 JSON body 全文） | 核对缺参/类型/格式 |
| 3 | 返回原文：HTTP 状态码 + body 全文（含 `errorcode`） | 唯一可靠判据 |
| 4 | 报错时间点（含时区） | 对服务端日志 |
| 5 | 客户侧环境（浏览器还是后端 SDK、语言、是否跨域） | 判断 CORS/编码问题 |
| 6 | 是否必现；换终端、换接口、换账号是否同样失败 | 区分「接口问题」与「数据/设备问题」 |

> 客户只丢一句「你们 API 报错了」时，把这张表发过去，不要凭空猜。

## 第二步：按返回形态分流

### A. 没有正常 HTTP 响应（连不上）

| 现象 | 可能原因 | 建议动作 |
|---|---|---|
| 连接被拒绝 / 无法访问 | 端口未放通、CMS 服务未启动、地址写错 | 让客户 `telnet {HOST} {PORT}` 或 Test-NetConnection 验端口；确认用的是 **CMS 服务器**端口（例 `192.168.1.10:12056`），不是别的服务端口 |
| 请求超时 | 网络/VPN/防火墙、服务无响应、查询范围过大 | 同网段再测一次；缩小时间范围重试；同时看服务端 CPU/内存 |
| `404` | 路径拼错（大小写、漏 `/api/v1/basic`）、版本不一致 | 拿 `api_reference.md` 的路径逐字对照 |
| `500 / 502 / 503` | 服务端异常 / 反向代理异常 | 属服务端问题：收集时间点交研发；**不要**建议客户改代码绕过 |
| 浏览器报 CORS / 跨域 | 浏览器同源策略（服务端未开 CORS） | 让客户改成**后端调用**；或用服务器自带的 `h5demo` 页验证；jsonp（回调名 `callback`）也可绕开浏览器跨域 |

### B. 有 JSON 返回但 `errorcode != 200`

| 错误码 | 含义（原文） | 排查方向 |
|---|---|---|
| 200 | 成功 | — |
| 201 | 非法请求 Illegal request | 请求方式/路径不符（如该 POST 用了 GET） |
| 202 | 服务端错误 Server Error | 服务端异常，取时间点交研发 |
| 203 | 无权限 No yes authority | 该账号权限不足：查账号授权范围（分组/终端/功能），或换有权限的账号验证 |
| 204 | 授权过期 Authorization expired | `key` 过期：重新调 1.1 拿新 key（长期运行的程序要判 204 后自动重取） |
| 205 | 账号过期 | 账号有效期/停用，找管理员续期 |
| 206 | 用户名或密码错误 | 核对 1.1 的 `username`/`password`（注意 URL encode、大小写） |
| 207 | 请求参数数量异常 | 缺参或多传参：按 `api_reference.md` 的「请求参数」逐项对 |
| 208 | 请求格式错误 | body 不是合法 JSON、Content-Type 不对（POST 必须 `application/json`）、时间格式不对 |
| 209 | 检测到未授权的 key | `key` 没带（**POST 要放在 JSON body 里**）或用了别的服务器的 key |
| 210 | 授权 key 错误 | `key` 值错/被截断/带了多余空格或换行 |
| 211 | MD5 错误 | 相关接口的校验串算错（文档仅定义该码，具体算法需研发确认） |
| 212 | 无数据 No data | 查询条件没命中：时间范围、终端号、通道、分页；**先扩大范围重试一次** |
| 213 | 无设备 No device | `terid` 不存在或不属于该账号：用 2.4 验终端号是否存在、2.3 车牌↔终端号转换 |
| 214 | 无空间 No space | 服务端磁盘满：检查存储空间 |
| 215 | 无文件 No file | 目标录像/证据文件不在服务器：核对 `dir`/`eid` 与时间范围（任务是否已完成） |
| 216 | 参数内容不符合限制 | 时间格式、长度、取值范围超限（例 9.1 任务名 15 字符、`tasktype=0` 时时间必须早于今天） |
| 217 | 用户已登录 | 同一账号重复登录/并发限制：换账号或先在别处退出 |
| 300 / 301 | 数据库连接/操作异常 | 服务端问题（数据库）：交研发，附时间点 |
| 302 | 内部接口参数个数错误 | 服务端内部调用异常：交研发 |
| 400 | 终端查询录像日历失败 | 设备侧失败：确认设备在线、存储卡正常，再重试 |
| 401 | 终端不在线 | 设备离线：用 5.2/5.3 查在线状态与最后状态 |
| 402 | 终端检索服务忙 | 并发拉流/检索过多：降低并发、稍后重试 |
| 403 | 终端执行失败 | 指令被设备拒绝：确认设备型号/固件是否支持该指令 |

> 每个码的**详细触发场景、处置话术、要问客户什么**见 `error_codes.md`。

## 第三步：接口级易错点（按接口核对时必看）

- **鉴权**：`1.1` 用 GET + query 拿 `key`；**POST 接口的 key 必须放在 JSON body 里**（放 query 会 207/209/210）。后续每个请求都要带 key。
- **时间格式**：3.x/4.x/5.x/9.x/12.x/13.x/14.x/15.x 用 `YYYY-MM-DD HH:mm:ss`；**6.1 里程只到日期 `YYYY-MM-DD`**，且参数名首字母大写 `Starttime`/`Endtime`（写错易 207/212/216）。
- **terid 形态**：3.1/3.3/4.x/5.x/13.x/14.x 收**数组**（`["AE99873120"]`）；7.2/8.x/9.1 收**字符串**；传车牌号会 213/212（车牌需经 2.3 转终端号）。
- **chl 形态**：8.x 是逗号分隔字符串 `chl=1,2,3,4`；9.1 是整型数组 `[1,2,3,4]`。
- **dir 参数**：9.4 / 16.1 / 16.2 的 `dir` 是**服务器路径的 base64**（原文示例 `QzpcVmlkZW9ccXExMjM0...`）；未编码、双重编码或路径不存在会 404/215/216。
- **分页**：14.2 / 15.2 用 `page` / `count`；`page=-1` = 不分页返回全部（数据量大时很慢，可能超时）。
- **context 续查**：15.2 每次查询**必须带上一次返回的 `context`**（文档明确「每次返回内容可能变化」），不带或复用旧值会拿不到后续数据。
- **9.1 下载任务**：`tasktype=0`（黑盒）时 `starttime`/`endtime` **必须早于今天**；`name` 限 15 字符；`netmode` 空=全模式；返回 `taskid` 后用 9.2 查 `state`（-2 磁盘不足 / -5 连接数受限 / 4 任务失败 / 6 下载失败 / 8 任务过期）。
- **7.2 实时拉流**：需 `terid`/`chl`/`port`（端口来自 7.1）；`dt=MDVR`（N9M 设备**不传** `dt`）；设备离线会拿不到流。
- **15.x 证据中心**：`eid` 必须来自 15.1/15.2 的搜索结果；15.6 打包需要 `serverip`（可由 15.7 查证据存储服务器）；证据文件缺失多与存储服务器/告警有无关联。
- **11.1 远程操作**：`content` 是设备协议字符串（依 N9M 文档），不是普通参数。
- **10.1 实时订阅**：socket.io（`http://{HOST}:{PORT}`），`didArray` 传空数组=全量订阅，事件名 `sub_state`/`sub_gps`/`sub_alarm`/`sub_mileage`。

## 第四步：快速自检阶梯（让客户按顺序跑，能一次定位 90% 的客诉）

按顺序执行，**在哪一步断就在哪一步定性**（`{HOST}:{PORT}` 换成客户服务器）：

| 步 | 请求 | 通过标准 | 断在这里说明什么 |
|---|---|---|---|
| 1 | `GET /api/v1/basic/key?username=<账号>&password=<密码>` | `200` + `data.key` 有值 | 206=账号密码错、205=账号过期、217=已登录/并发限制、404=地址或版本不对 |
| 2 | `GET /api/v1/basic/groups?key=<上一步的 key>` | `200` + 有分组数据 | 210/209=key 传错或没带上、204=key 过期（间隔太久）、203=账号无基础权限 |
| 3 | `GET /api/v1/basic/devices?key=<key>` | `200` + 能看到车/终端 | 203=该账号看不到任何终端、212/213=账号下无设备 |
| 4 | `GET /api/v1/basic/devices/exist?terid=<终端号>&key=<key>` | `data.result = true` | 目标终端号写错、或不属于该账号（可用 2.3 车牌→终端号） |
| 5 | 客户实际报错的那个接口（POST 记得 key 在 body 里） | `200` | 按第二步错误码表定性；业务类（212/213/215/401/402/403）继续查数据与设备 |

补充判断：

- 第 2 步 200 而第 5 步 203 → **权限/功能授权**问题，不是接口问题（让客户用有权限的账号复测对比）。
- 第 5 步时好时坏、大量并发时 402 → 并发/资源问题（降并发、错峰）。
- 所有 POST 都 207/209 而 GET 正常 → 十有八九是 **POST 没把 `key` 放进 JSON body** 或缺 `Content-Type: application/json`。
- 客户说「文档里没有这个接口/字段」→ 先问 **CMS 服务器版本**（本技能依据 2.6.3），版本差异要按现场版本核对。

## 最小复现示例（可直接发给客户）

```powershell
# 1) 取 key（GET，参数在 query）
curl "http://192.168.1.10:12056/api/v1/basic/key?username=admin&password=admin"

# 2) 用 key 调一个只读接口自检（200 = key 与基础权限都正常）
curl "http://192.168.1.10:12056/api/v1/basic/groups?key=<KEY>"

# 3) POST 接口：key 必须放进 JSON body，并带 Content-Type
curl -X POST "http://192.168.1.10:12056/api/v1/basic/gps/count" ^
  -H "Content-Type: application/json" ^
  -d "{\"key\":\"<KEY>\",\"terid\":[\"AE99873120\"],\"starttime\":\"2026-09-29 00:00:00\",\"endtime\":\"2026-09-29 23:59:59\"}"
```

> 让客户**原样**把这三条的输出（含 HTTP 状态码）贴回来，比让他描述「报错了」有用得多。

## 第五步：输出格式（固定四段，别省）

1. **结论**：最可能原因 + 置信度（高/中/待确认）。
2. **依据**：错误码 / 文档章节 / 字段名（例「2.3 车牌转终端号失败 → 213」）。
3. **要客户做的**：按可能性排序的具体动作，含可复制的核对点（URL/参数名/格式）。
4. **参考回复**：可直接转给客户的中文与英文话术（模板见 `cases.md`）。

## 禁止事项

- 不编造错误码含义、不臆测服务端内部实现；文档未定义的码一律说「未定义，需研发确认」。
- 不承诺「已修复 / 下次一定好」；不指导客户改数据库、关防火墙、跳过鉴权或伪造 key。
- 不输出真实客户账号、密码、key、token。
- 不把「无数据（212/213/215）」直接说成「接口坏了」——先按数据/设备方向查。
