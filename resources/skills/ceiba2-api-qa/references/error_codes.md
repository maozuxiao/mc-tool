# Ceiba2 / WCMS5 错误码逐条处置（Appendix 1 展开）

> 依据官方文档 **v2.6.3** Appendix 1。原文只给了英文短语（见下表「原文」列），下面补充的是**排查经验与处置动作**
> —— 属于工程判断，不是文档原文；对外沟通时以「可能原因」表述，不要当成官方结论。

**统一用法**：客户报错 → 先看他在**第几步**（配合 `SKILL.md` 的「快速自检阶梯」）→ 查本表 → 输出「结论 + 依据 + 动作 + 话术」。

## 鉴权类（204 / 209 / 210 / 203 / 205 / 206 / 217）

### 200 — Request successful
成功。注意：**HTTP 200 不等于业务成功** —— 必须同时看 body 里的 `errorcode`。有客户只看 HTTP 状态码就报「接口正常但没数据」。

### 204 — Authorization expired（授权过期）
- **典型触发**：`key` 领取后长时间未用；CMS 服务/账号重新登录导致旧 key 失效；同一 key 换到别的服务器用。
- **怎么确认**：把该 key 放回 `2.1 GET /api/v1/basic/groups?key=<KEY>` 复测 → 仍 204 即已过期。
- **204 与 210 的区别**：204 = key 曾经有效但**已过期**；210 = key **本身不对**（抄错、截断、带空格）。
- **处置**：重新调 `1.1` 取 key；集成方程序里对 204 做「自动重取 key 并重试一次」，不要硬编码长期使用的 key。
- **问客户**：key 是何时取的？是否有多个进程/多台机器共用同一个 key？期间是否重启过 CMS 或重新登录过？

### 209 — Unauthorized key detected（检测到未授权的 key）
- **典型触发**：请求**没带 key**；POST 接口把 key 放在 query 而不是 JSON body；用了另一套环境的 key。
- **怎么确认**：检查 POST 的 body 里是否有 `"key"` 字段（这是最常见的坑）。
- **处置**：GET 把 key 放 query、POST 把 key 放进 JSON body；补上后再试。
- **问客户**：把请求的完整 body（POST）或完整 URL（GET）贴过来。

### 210 — Authorization key error（授权 key 错误）
- **典型触发**：key 值抄错/被截断/复制时带了换行或空格；URL 未编码导致特殊字符丢失。
- **处置**：重新复制 key；确认没有前后空白；必要时 `urlencode` 后再拼。
- **问客户**：key 是否从 1.1 的返回里**原样**取的？

### 203 — No yes authority（无权限）
- **典型触发**：账号没被授权该功能/该分组/该终端；功能模块未购买或未授权（如证据中心、客流、人脸比对）。
- **怎么确认**：用另一个有权限的账号调同一接口对比；或调 `2.5 GET /api/v1/basic/authority` 看权限位。
- **处置**：由管理员在 CMS 里给该账号补权限/加设备范围，而不是改接口调用方式。
- **问客户**：该账号在网页端能看到对应功能与设备吗？（网页端也看不到 → 权限问题；网页端正常 → 再看 key/参数）

### 205 — Account has expired（账号过期）
- **处置**：找管理员续期/启用账号；顺带确认账号未被停用。
- **问客户**：该账号有效期到什么时候？是否被别人停用过？

### 206 — Username and password are incorrect（用户名或密码错误）
- **典型触发**：密码里有 `@ # & + 空格` 等字符但没做 URL encode；大小写不符；账号前后带空格。
- **处置**：对密码做 `urlencode`；确认账号是最新的。
- **问客户**：能否用同一账号密码正常登录网页端（排除密码过期/被改）？

### 217 — User logged in（用户已登录）
- **典型触发**：账号有并发登录限制，集成程序与网页端/其他程序同时登录；程序反复登录未退出。
- **处置**：换专用集成账号，或先在别处退出；程序复用已取得的 key 而不是反复调 1.1。
- **问客户**：是不是多台机器/多个进程用同一个账号？

## 参数与请求格式类（201 / 207 / 208 / 216 / 302 / 211）

### 201 — Illegal request（非法请求）
- **典型触发**：方法不对（该 POST 用了 GET）、路径不对、带了非法字符、Content-Type 不符。
- **处置**：按 `references/api_reference.md` 核对「方式 + 路径」，POST 必须 `Content-Type: application/json`。

### 207 — Request parameter number exception（请求参数数量异常）
- **典型触发**：**缺参**（最常见：POST 少 key、缺 `terid`/`starttime`/`endtime`）或多传了不认识的字段。
- **最常见坑**：`6.1 里程` 参数名是 `Starttime`/`Endtime`（大写首字母），写成 `starttime` 会被当作缺参。
- **处置**：按接口的「请求参数」逐项对照；参数名**大小写敏感**。

### 208 — Request format error（请求格式错误）
- **典型触发**：body 不是合法 JSON（尾逗号、单引号、中文引号）；POST 忘了 Content-Type；GET 参数未 encode；时间格式不是 `YYYY-MM-DD HH:mm:ss`。
- **处置**：用文档示例 body 原样替换后逐步改；JSON 校验工具先过一遍。

### 216 — Request parameter content does not meet the restrictions（参数内容不符合限制）
- **典型触发**：超长度/超范围的取值，例如：
  - `9.1` 任务名 `name` 限 **15 字符**；
  - `9.1` `tasktype=0`（黑盒）时 `starttime/endtime` **必须早于今天**；
  - 时间跨度超过服务端允许的最大范围（录像检索类）；
  - `15.2` 分页 `count` 过大。
- **处置**：缩小时间范围、修正取值；把客户的入参与文档限制逐条对照。
- **问客户**：完整参数（含时间范围）是多少？

### 302 — Internal interface parameter number error（内部接口参数个数错误）
属**服务端内部**异常（不是客户参数问题）：收集时间点 + 请求，交研发。

### 211 — MD5 error
文档只定义了该错误码，未给出算法。客户遇到时：让其提供**完整请求（含全部参数与签名串来源）**，交研发按现场版本确认签名规则；**不要**自行编造签名算法。

## 业务数据类（212 / 214 / 215 / 400）

### 212 — No data（无数据）
- **典型触发**：时间范围没覆盖到数据、终端号不对、通道不对、分页越界、查询条件过严（先把条件放宽重试一次）。
- **处置顺序**：① 把时间范围放大（例：整天 → 前后各一天）；② 用 `2.4` 确认终端号存在；③ 换 `terid`/`chl` 单值试；④ 用同接口查一个**已知有数据**的终端做对照。
- **问客户**：同一个接口查另一个终端有没有数据？（有 → 数据/设备问题；都没有 → 参数或权限问题）
- **别忘**：`212` 不等于「接口坏了」。

### 214 — No space（无空间）
服务端磁盘满：检查服务器存储（录像盘/证据盘），清理或扩容后再试。

### 215 — No file（无文件）
- **典型触发**：目标录像/证据文件不存在或已被清理；`dir` 路径不对（9.4/16.x 的 `dir` 需 base64）；下载任务未完成就取文件。
- **处置**：先用 `8.1/8.2` 或 `9.2/9.3` 确认文件确实存在且任务 `state=3（完成）`，再取文件。

### 400 — Terminal search video calendar fail（终端查询录像日历失败）
- **典型触发**：设备离线或存储卡异常导致设备侧查询超时；设备固件不支持日历查询。
- **处置**：先 `5.2/5.3` 确认在线与最后状态；设备在线仍失败 → 查存储卡/固件，交研发。

## 设备与终端类（401 / 402 / 403）

### 401 — Terminal is not Online（终端不在线）
- **处置**：`5.2 GET /api/v1/basic/state/now`（在线列表）/ `5.3 state/last`（最后状态）确认；让客户检查设备供电、SIM 流量、注册服务器地址。
- **话术要点**：这是**设备未上线**，不是接口故障；设备上线后重试即可。

### 402 — The terminal retrieval service is busy（终端检索服务忙）
- **典型触发**：并发拉流/检索过多；同一设备被多次同时拉流（含多个集成方同时跑）。
- **处置**：降低并发（建议串行或限流）、错峰重试；确认没有别的程序在同时拉同一设备。

### 403 — Terminal execution fail（终端执行失败）
- **典型触发**：设备拒绝指令（该型号/固件不支持该操作）、设备侧忙、通道号非法。
- **处置**：确认设备型号与固件是否支持该指令（例：`11.1` 远程操作依赖 N9M 协议）；换通道/换设备复测。

## 服务端异常类（202 / 300 / 301）

- **202 Server Error**：服务端异常。收集**时间点 + 请求 + 返回**交研发。
- **300 Database connection error** / **301 Database operation exception**：数据库连接或操作异常（服务端问题）：交研发，附时间点与影响范围。
- 这三类**不要**让客户改调用方式或重试到成功为止；应如实告知「服务端异常，已记录待研发处理」，并给临时规避（稍后重试/换接口）。
